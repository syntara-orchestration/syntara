# Execution Plane service isolation: revisit decisions

Recorded 1 October 2026 from the first architecture review. These are accepted defaults for the first service release, with explicit triggers for reconsidering them. They are not blockers to drafting the initial API contract.

## Accepted first-release defaults

| Topic | Start with | Revisit when |
| --- | --- | --- |
| EP unavailable during AO submission | Retry with the same stable request ID for a bounded period, up to the workflow deadline; then return a clear service-unavailable error. Never fall back to local execution after an ambiguous submission. | Before finalizing workflow timeout/retry settings, then after the first operational review using retry volume, queue age, and outage data. Decide whether longer queuing or a different failure policy is needed. |
| Save an AO integration while EP is setting it up | Save the AO integration and show `pending`; retry EP synchronization and show `ready` or `error`. Do not make the execution target available to new work until EP reports it ready. | Revisit before enabling this behavior for production users, and after observing setup failures and user recovery needs. Confirm whether users need retry controls or whether some integration types should block save. |
| Result delivery | EP sends authenticated callbacks to AO. AO records callbacks durably and reconciles missing results against EP status. | Before the first cross-network deployment, verify that the real network permits EP-to-AO callbacks. Revisit after delivery-lag/retry metrics show whether callback delivery remains a good primary path. If inbound callbacks cannot be allowed, make AO polling the primary path. |
| EP clients | AO is the only authorized client in release one. Include client identity and project scope in the contract so a later release can add clients without trusting caller-supplied scope. | Before onboarding the second client. Review client registration, grant administration, quotas, audit attribution, and compatibility with existing AO authorization. |
| Integration credentials | AO remains the source for user-entered credentials. Send versioned credential updates through an authenticated write-only operation and store EP's execution copy under EP-owned secret management. Ordinary rotation changes new launches; bounded active jobs may finish. Emergency revocation has a separate stop/revoke path. | Before production credential provisioning and before the first rotation/revocation exercise. Confirm storage/key ownership, expiry and retry behavior, active-job policy, cleanup, and audit evidence with the platform/security owners. |
| Ambiguous execution outcome | EP reports `reconciliation_required` and retries observation of the deterministic Job without launching another one. Do not automatically rerun if a crash leaves it unclear whether the script or its side effects completed; require an explicit retry decision. | Before adding automatic retries for uncertain outcomes, or if operational data shows reconciliation is frequent. Define which workload types can safely opt into idempotent reruns and how an operator resolves a Job that is permanently missing. |
| Workflow cancellation | AO stores cancellation intent in its own database and retries EP cancellation by stable request ID, including a cancellation tombstone if submission has not arrived. EP reports `cancel_requested` while a dispatched Job is stopping and reports `cancelled` only after foreground deletion removes the Job and its pods. A terminal workload result wins if completion is observed first. | Validate with Temporal cancel races, lost HTTP acknowledgements, controller restart, and real-cluster termination tests before release. Review manual handling when a previously dispatched Job disappears and its outcome cannot be recovered. |
| User workload isolation | EP creates a deterministic Kubernetes Job per accepted work item. The pod has no service-account token, a job-only input Secret, bounded CPU/memory and temporary storage, a read-only root filesystem, dropped Linux capabilities, and a NetworkPolicy. Default egress is DNS-only; an operator-approved CIDR allowlist is needed for scripts that call external systems. The controller uses each integration's verified CA certificate. | Before the first production workload, confirm target-cluster RBAC and CNI enforcement, workload image distribution, allowed/forbidden CIDRs, timeout and cleanup behavior, and that pods cannot reach AO/EP databases, Temporal, or service-management endpoints. NetworkPolicy objects alone do not prove that a cluster CNI enforces policy. |
| Kubernetes API TLS | Require HTTPS and certificate validation for EP-to-target-cluster API calls. AO integration CA certificates are copied through the authenticated outbox and encrypted in EP; disabling certificate verification is rejected for EP-managed OpenShift targets. | Revisit only if platform PKI or certificate rotation requires another trust mechanism. Do not add a verification bypass as a workaround for missing CA configuration. |

## Confirmed database choice for release one

Use the existing PostgreSQL server with a distinct EP database, separate AO and EP runtime roles, restricted migration roles, and database-local grants. Revoke `CONNECT` from `PUBLIC` on both owned databases and grant it only to their runtime/migration roles. AO credentials must not connect to or read the EP database; EP credentials must not connect to or read the AO database. This creates service and database ownership boundaries while accepting the existing server as a shared availability and maintenance failure domain. The local compose bootstrap and EP migration enforce the EP side; production database provisioning must enforce the matching AO database grant policy.

Revisit a separate PostgreSQL server if EP needs independent availability/maintenance windows, resource isolation, backup/restore objectives, compliance controls, or recovery from a server-level failure without AO impact. Measure those needs after the service is operating; a separate server is not a release-one prerequisite.

## Decision to revisit: saving an integration before EP is ready

For example, a user saves an OpenShift integration in AO. AO stores its configuration in the AO database, and EP must create the matching cluster and execution target in the EP database. If EP is unavailable at that moment, the services cannot commit both databases as one transaction.

Start with saving the integration and showing `pending`; work that needs its execution target waits until EP reports `ready`. Keep sync errors visible and retryable. Revisit this before production users rely on it.

The alternative is rejecting the save until EP confirms the cluster. That makes the form appear synchronous, but if EP created the cluster and AO lost the response, AO still needs reconciliation before retrying or deleting it.

This behavior uses the durable synchronization outbox in the service plan. Revisit the user-facing status and retry controls after setup failure cases are observed in production.

## Workload network policy and deployment gates

The controller creates a per-work-item policy before the Secret and Job. It denies ingress and permits egress only to cluster DNS and the configured CIDR allowlist. Operators must review any allowed ranges against the AO API, Temporal, EP management API, both databases, and other sensitive services. The initial allowlist is deployment-wide rather than an AO user's per-workload choice; revisit per-target or per-workload egress grants before adding clients with different network needs.

Each target-cluster credential must permit creation, observation, and foreground deletion of Jobs, Secrets, Pods, Pod logs, and NetworkPolicies in the execution namespace. Validate those permissions with the platform owner. NetworkPolicy enforcement depends on the target cluster CNI, so a successful API response is not sufficient evidence. The first production gate includes a live-cluster test proving forbidden traffic fails, cancellation/timeout cleanup, and recovery after controller restarts. The current implementation is not a substitute for that evidence.
