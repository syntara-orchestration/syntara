# Architecture Decision Records

The following document details our architectural decisions made for the Nexus Platform.

| Question                                              | Decision                                                                    | Decision Date | Details                                                                                                                                                               |
|-------------------------------------------------------|-----------------------------------------------------------------------------|---------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| What orchestration engine backend will we use?        | [Temporal](https://github.com/temporalio/temporal)                          | 09/12/2025    | We have decided to leverage Temporal for our backend workflow engine due to its mature capabilities around reliable execution, scalability, visibility and more.      |
| Django or FastAPI?                                    | [FastAPI](https://fastapi.tiangolo.com/)                                    | 10/03/2025    | We have decided to use FastAPI for our Python backend, due to its mature async capabilities, speed benefits, and widespread adoption in the AI ecosystem              |
| Soft Delete or Hard Deletes?                          | **Superseded** — see "Hard Deletes Only" below                              | 10/07/2025    | Originally decided on soft deletes. Superseded by the "Hard Deletes Only" decision after architectural review concluded soft deletes added unnecessary complexity.    |
| UUID or ID?                                           | UUID                                                                        | 10/07/2025    | For ID fields, we should primarily use UUIDs instead of auto-incrementing IDs where possible                                                                          |
| HTTP PATCH support                                    | PATCH                                                                       | 10/09/2025    | Our OpenAPI specifications should support PATCH where appropriate                                                                                                     |
| Should top-level components be in their own subfolder | Yes                                                                         | 10/10/2025    | Each top-level component; e.g. workflow, core-agent, tool-registry etc, should be in sub-folders of `/src/` and included in `pyproject.toml`'s `packages` section.    |
| Should Python packages share a common namespace       | Yes — consolidate under `syntara`                                             | 10/20/2025    | All first-party packages now live under the parent `nexus` namespace (`syntara.api`, `syntara.agents`, `syntara.tool_manager`) for clearer imports, tooling, and packaging. |
| podman-compose vs kind vs CRC                         | podman-compose                                                              | 10/10/2025    | Local development will utilize `podman-compose`. We can move to a k8s environment later.                                                                              |
| SSE vs WebSockets for streaming API                   | WebSockets                                                                  | 10/10/2025    | Streaming APIs will use WebSockets. CRUD operations will continue to use RESTful API.                                                                                 |
| What library/ies will we use for models?              | [SQLModel](https://sqlmodel.tiangolo.com/)                                  | 10/15/2025    | SQLModel is built on top of both SQLAlchemy and Pydantic, allowing us to create one model for both database and API resources                                         |
| What key/value store will we use?                     | [Redis](https://redis.io/)                                                  | 01/28/2026    | Redis is a mature, well-supported caching solution with broad ecosystem adoption.                                                                                     |
| Logging format?                                       | Structured logging with [structlog](https://www.structlog.org/en/stable/) | 01/30/2026  | `structlog` is _the_ production-ready logging solution for Python!                                                                                                    |
| Separate database for audit events?                   | **Retired** — OTEL is the single telemetry path            | 04/16/2026  | Originally used a dedicated `nexus_audit` database. Retired: audit events now flow through the transactional outbox in the main database and are exported exclusively via the OTEL Collector. The `audit_events` table, separate session factory, and Alembic migration environment have been removed. |
| Hard Deletes Only                                     | Hard Delete                                                                 | 06/25/2026    | All resource deletions use hard deletes. Soft delete infrastructure (`SoftDeletableResource`, `deleted_at`/`deleted_by` fields, automatic query filtering) is removed. Audit history is captured through the observability pipeline (OTEL), not by retaining soft-deleted rows. Supersedes the earlier "Soft Delete" decision. |
| How should system operations (document conversion, agent execution) be executed? | Temporal built-in workflows on a dedicated task queue — replacing FastAPI `BackgroundTasks` | 07/01/2026 | `BackgroundTasks` execute on the API event loop, competing directly with HTTP request handling. Benchmarking showed a 7× p50 latency spike at 5 concurrent requests and silent work loss on pod crash at 20+ concurrent. System operations are now defined as built-in Temporal workflows (`is_builtin=True`) and dispatched to a dedicated `orchestrator-background-queue` worker, isolating them from user workflow execution. |
| How should background worker autoscaling be implemented — KEDA or CPU-based HPA? | CPU-based HPA (50% utilisation target) for v1; KEDA deferred | 07/01/2026 | KEDA's native Temporal scaler (queue-depth based) is the ideal signal for I/O-bound workers, but requires the "Custom Metrics Autoscaler" cluster operator install (cluster-admin privilege). This adds a cluster-wide infrastructure dependency. CPU-based HPA is available without additional operators and is sufficient for v1. |
| PgBouncer or increasing PostgreSQL `max_connections` for horizontal scaling? | Increase `max_connections` to 200–300; PgBouncer deferred | 07/01/2026 | Benchmarking showed PgBouncer in transaction mode caps throughput at 7.8 wf/s versus 16–17 wf/s without it, due to the connection overhead on Temporal's short-lived queries. Raising `max_connections` to 200 (default profile) or 300 (large profile) eliminates connection exhaustion at 4+ worker replicas with no throughput penalty and no additional infrastructure. PgBouncer is only reconsidered if multiple services share the same PostgreSQL instance. |
| What value should `NUM_HISTORY_SHARDS` be set to in the Temporal operator deployment? | 512 (Temporal production minimum) — not the hardcoded default of 4 | 07/01/2026 | `NUM_HISTORY_SHARDS` is **immutable after database creation**. The current operator hardcodes `4` (Temporal's development default). Benchmarking shows 512 shards yields 14% throughput improvement and 52% lower scheduling latency compared to 4. Deploying to production with 4 shards requires a destructive database migration to correct later. The operator must set this to 512 before any production deployment. |
