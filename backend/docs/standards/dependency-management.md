# Dependency Management Standards

This document defines dependency management standards for the Syntara Python monorepo.

## Package Manager

Use `uv` exclusively for all dependency management operations. Do not use `pip`, `poetry`, or other package managers.

## File Roles

### pyproject.toml

Source of intent for dependency constraints. Declares version ranges using semantic versioning patterns.

- Defines production dependencies in `[project.dependencies]`
- Defines development dependencies in `[project.optional-dependencies.dev]`
- Specifies Python version requirement: `requires-python = ">=3.12,<3.14"`

### uv.lock

Source of truth for reproducibility. Contains exact pinned versions with cryptographic hashes.

- Autogenerated by `uv sync`
- Never edit manually
- Commit with every pyproject.toml change

### requirements.txt

Synced to uv.lock for compatibility with other build systems.
- Autogenerated by `uv export`
- Includes exact versions and cryptographic hashes
- Excludes dev dependencies, editable installs, and workspace references
- Generation command: `uv export --frozen --python=3.12 --no-dev --no-editable --no-emit-workspace --output-file requirements.txt`

### requirements-build.txt

Build-time dependencies for hermetic/offline container builds.

- Manually curated
- Includes `uv` and `hatchling` with cryptographic hashes

## Version Pinning Strategy

Choose the appropriate constraint pattern based on the library's maturity and stability:

### Stable, Mature Libraries (minimum version only)

For libraries with strong semver guarantees and stable APIs:

```
"asyncpg>=0.30.0"
"redis>=7.1.0"
"pydantic>=2.0.0"
"alembic>=1.12.0"
```

**When to use**: well-established libraries (1.0+) with a track record of semver compliance.

### Libraries with Known Breaking Changes (upper bound)

For libraries that have a history of breaking changes in minor versions:

```
"fastapi>=0.104.0,<0.122"
"sqlalchemy[asyncio]>=2.0.0,<2.0.45"
"ruff>=0.1.0,<0.14.4"
"mypy>=1.6.0,<1.19"
```

**When to use**: libraries that introduce API changes or deprecations frequently.

### Pre-1.0 Libraries (strict minor version control)

For libraries under active development without semver guarantees:

```
"sqlmodel>=0.0.14,<0.0.28"
"langchain-mcp-adapters>=0.1.0,<0.2.0"
"pymupdf>=1.26.6,<1.27.0"
```

**When to use**: all libraries with major version 0.x, where minor version bumps may break compatibility.

### Development Dependencies

Apply the same patterns to dependencies in `[project.optional-dependencies.dev]`. Treat linters, type checkers, and test frameworks with the same care as production dependencies.

## Adding a New Dependency

1. Add the dependency to `pyproject.toml` with appropriate version constraint:
   ```toml
   [project.dependencies]
   "new-library>=1.2.0,<2.0.0"
   ```

2. Update uv.lock:
   ```bash
   uv sync --extra dev
   ```

3. Update requirements.txt:
   ```bash
   make sync-requirements
   ```

4. Commit all three files together:
   - pyproject.toml
   - uv.lock
   - requirements.txt

Never commit only pyproject.toml or only uv.lock. All three files must be synchronized.

## Removing a Dependency

1. Remove the dependency from `pyproject.toml`

2. Update uv.lock:
   ```bash
   uv sync --extra dev
   ```

3. Update requirements.txt:
   ```bash
   make sync-requirements
   ```

4. Commit all three files together

5. Search for imports and references:
   ```bash
   grep -r "import removed_library" src/ tests/
   ```

## Updating Dependencies

### Automated Updates (Renovate)

MintMaker (Renovate) automatically creates PRs for dependency updates:

- Schedule: before 6am on Monday (weekly)
- Strategy: `in-range-only` (only updates within declared version ranges)
- Grouping:
  - **Minor/patch** updates grouped into a single PR (`python dependencies (minor)`)
  - **Major** updates grouped into a separate PR (`python dependencies (major)`)
- Auto-merge: **disabled** - all PRs require manual review and approval
- `requirements.txt` is **not** managed by Renovate directly (it is a generated file). The `konflux-requirements-sync.yml` GitHub Action auto-syncs it when `uv.lock` changes in MintMaker PRs.

Review Renovate PRs for:
- Breaking changes in release notes
- Test failures in CI
- Performance regressions
- **Snyk SCA vulnerability findings** (see Vulnerability Scanning below)

### Manual Updates

To update a specific dependency:

1. Modify the version constraint in pyproject.toml (if needed)

2. Run:
   ```bash
   uv sync --extra dev --upgrade-package <package-name>
   make sync-requirements
   ```

3. Commit pyproject.toml, uv.lock, and requirements.txt together

To update all dependencies within constraints:

```bash
uv sync --extra dev --upgrade
make sync-requirements
```

## Vulnerability Scanning

### Snyk Security Scanning

Syntara uses Snyk for two types of security scanning:

**SAST (Static Application Security Testing):**
- Analyzes application code for security vulnerabilities (SQL injection, XSS, hardcoded secrets, etc.)
- Workflow file: `.github/workflows/sast-snyk.yml` (scans both backend and frontend)
- **Uses differential scanning**: only blocks PRs on NEW HIGH/CRITICAL vulnerabilities
- Scheduled daily at 2:23 PM UTC

**When SAST runs:**
- **On pull requests** (differential mode - only blocks on NEW HIGH/CRITICAL findings)
- On pushes to `devel` branch (blocks on ANY HIGH/CRITICAL)
- Scheduled daily at 2:23 PM UTC (blocks on ANY HIGH/CRITICAL)
- On-demand via workflow_dispatch

**How differential SAST works:**

For pull requests:
1. Scans code in the **PR branch** (without severity filtering - captures all vulnerabilities)
2. Scans code in the **base branch** (`devel`) (without severity filtering - captures all vulnerabilities)
3. Compares SARIF results and **blocks only on NEW HIGH/CRITICAL vulnerabilities**
   - HIGH/CRITICAL severity is identified by `level: "error"` in Snyk's SARIF output
   - Vulnerabilities are compared by `ruleId` to identify new vs pre-existing findings
   - Scans run without `--severity-threshold` to ensure complete comparison (prevents missing cases where severity changes)

This means:
- ✅ PR passes if it doesn't introduce new code vulnerabilities
- ❌ PR fails if new code introduces HIGH/CRITICAL vulnerabilities
- ✅ Pre-existing vulnerabilities in base branch don't block the PR
- ✅ Correctly handles cases where a vulnerability's severity changes between branches

For push/schedule events: Uses `--severity-threshold=high` to block on ANY HIGH/CRITICAL (traditional behavior)

**CI Integration:**
- SAST is integrated into the `required-checks` gate in `.github/workflows/ci-backend.yml`
- If SAST fails, the PR cannot merge

**SCA (Software Composition Analysis):**
- Scans dependencies for known CVEs
- Uses differential scanning: only blocks PRs on NEW vulnerabilities introduced by the PR
- Runs only when dependency files change (to reduce noise on feature PRs)
- Workflow file: `.github/workflows/sca-snyk.yml` (two jobs: Python and npm)
- Smart conditionals: only runs relevant job based on which dependency files changed

**When SCA runs:**
- On pull requests that modify dependency files:
  - Backend: `backend/pyproject.toml`, `backend/requirements*.txt`, `backend/src/*/pyproject.toml`
  - Frontend: `frontend/package.json`, `frontend/package-lock.json`, `frontend/packages/*/package.json`
- Scheduled daily at 2:23 PM UTC (catches newly-disclosed CVEs)
- On pushes to `devel` branch
- On-demand via workflow_dispatch

**How SCA works for pull requests (differential scanning):**

For each PR that modifies dependency files:
1. Scans dependencies in the **base branch** (target branch state)
2. Scans dependencies in the **PR branch** (proposed changes)
3. Compares results and **blocks only on NEW HIGH/CRITICAL vulnerabilities**

This means:
- ✅ PR passes if it doesn't introduce new vulnerabilities
- ❌ PR fails if bumping a dependency introduces new HIGH/CRITICAL vulnerabilities
- ✅ Pre-existing vulnerabilities in base branch don't block the PR
- ✅ Metadata-only changes (e.g., updating `description` in pyproject.toml) pass
- ✅ Handles transitive dependencies correctly (if bumping B brings in vulnerable C, PR is blocked)

**Examples:**

*Example 1: Pre-existing vulnerability doesn't block*
- Base: Library A has CVE-2024-1234 (HIGH), Library B v1.0
- PR: Bumps Library B v1.0 → v2.0 (clean)
- Result: ✅ **PR passes** (CVE-2024-1234 existed before this PR)

*Example 2: New vulnerability blocks*
- Base: Library B v1.0 (no known vulnerabilities)
- PR: Bumps Library B v1.0 → v2.0 (has CVE-2024-5678 HIGH)
- Result: ❌ **PR blocked** (new vulnerability introduced)

*Example 3: Transitive dependency vulnerability blocks*
- Base: Library B v1.0 (no vulnerable dependencies)
- PR: Bumps Library B v1.0 → v2.0 (brings in Library C with CVE-2024-9999 HIGH)
- Result: ❌ **PR blocked** (transitive vulnerability introduced)

**What it checks:**
- Python dependencies (via `requirements.txt`)
- npm dependencies (via `package.json` in `frontend/`)

**Severity thresholds:**
- **HIGH/CRITICAL**: Blocks PR merge only if NEW (not pre-existing)
- **MEDIUM/LOW**: Reported but does not block merge
- **For push/schedule events**: Blocks on ANY HIGH/CRITICAL (traditional behavior)

### Manual Review Policy

All dependency update PRs require manual review and approval before merge:

**Review checklist:**
- Verify no HIGH or CRITICAL vulnerabilities detected by Snyk SCA
- Review breaking changes in release notes
- Confirm all CI checks pass
- Assess security advisory details if vulnerabilities are present

**Security-first approach:**
Auto-merge is disabled to ensure human review of all dependency changes and prevent potential malware/attack risks.

### Responding to Vulnerability Alerts

When Snyk (SAST or SCA) detects a HIGH/CRITICAL vulnerability:

1. **Review the finding**: understand the impact, affected code/dependency, and severity
2. **Check for available fix**:
   - **SAST**: Review remediation guidance in the finding details
   - **SCA**: Determine if a patched dependency version exists
3. **Assess applicability**: confirm if the vulnerability affects your code paths
4. **Remediation options:**
   - Fix the code or update to a patched version (preferred)
   - Apply a workaround if no patch is available
   - Request an exception if it's a false positive (see below)
5. **Document decision**: add comment to PR explaining the chosen approach

For MEDIUM/LOW severity findings:
- Review during normal PR review process
- Plan remediation during next dependency update cycle

### Handling False Positives

If a SAST or SCA finding is a false positive:

**For SAST (code vulnerabilities):**
1. **Verify it's genuinely a false positive** — confirm the code path cannot be exploited
2. **Comment on the PR** with:
   - Rule ID (e.g., `SNYK-CODE-0001`)
   - File and line number
   - Technical justification for why it's a false positive
3. **Request maintainer review** — a maintainer with Snyk organization access will review the justification and mark it as ignored in the Snyk dashboard if approved

**For SCA (dependency vulnerabilities):**
1. **Document why the vulnerability doesn't apply**:
   - CVE ID
   - Package name and version
   - Reason (unused code path, sandboxed environment, etc.)
   - Remediation timeline if a fix is expected soon
2. **Request maintainer review** — a maintainer will review the justification and mark it as ignored in the Snyk dashboard if approved

**Important:** False positive exceptions are tracked in the Snyk dashboard, not in code comments. This allows centralized management and prevents exceptions from becoming stale as code evolves.

## Enforcement

### Pre-commit Hook

The `sync-requirements` pre-commit hook automatically runs when `uv.lock` or `pyproject.toml` changes:

```yaml
- id: sync-requirements
  name: sync requirements.txt with uv.lock
  entry: make
  args: [sync-requirements]
  language: system
  pass_filenames: false
  files: ^(uv\.lock|pyproject\.toml|requirements\.txt)$
```

### CI Checks

The requirements sync workflow fails if requirements.txt is out of sync:

```yaml
- name: Check requirements.txt sync
  run: make sync-requirements
```

If CI fails on requirements sync:
1. Run `make sync-requirements` locally
2. Commit the updated requirements.txt
3. Push the commit

## Common Pitfalls

### Forgetting to Sync requirements.txt

**Wrong**:
```bash
uv sync --extra dev
git add pyproject.toml uv.lock
git commit -m "Add new dependency"
```

**Correct**:
```bash
uv sync --extra dev
make sync-requirements
git add pyproject.toml uv.lock requirements.txt
git commit -m "Add new dependency"
```

The pre-commit hook will catch this, but it's better to sync proactively.

### Using Overly Broad Constraints

**Wrong**:
```toml
"pydantic>=2.0.0"  # for a pre-1.0 library
```

**Correct**:
```toml
"sqlmodel>=0.0.14,<0.0.28"  # strict minor control for 0.x
```

### Manually Editing uv.lock or requirements.txt

Never edit these files manually. Always regenerate them:

- uv.lock: `uv sync --extra dev`
- requirements.txt: `make sync-requirements`

## Tooling vs Convention

**Enforced by tooling:**

- `sync-requirements` pre-commit hook (catches out-of-sync requirements.txt)
- CI requirements sync check (fails build if requirements.txt diverges)
- `uv sync` validates dependency resolution (catches conflicts)
- `uv.lock` integrity (cryptographic hashes prevent tampering)

**Convention only:**

- Version constraint strategy (minimum-only vs upper-bounded vs strict minor)
- Committing all three files together (pyproject.toml, uv.lock, requirements.txt)
- Dependency review for Renovate PRs
- Python version policy updates
