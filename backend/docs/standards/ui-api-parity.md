# UI-API Parity Standards

Standards for maintaining functional parity between the backend REST API and the frontend UI.

## Overview

Nexus ensures UI-API parity by design: the frontend communicates exclusively through typed API clients generated from the backend's OpenAPI spec. Every UI capability has a corresponding REST endpoint — if the UI can do it, the API can do it. This document codifies the conventions that maintain that property as the codebase evolves.

## Typed API Clients

All frontend API calls MUST use the typed `openapi-fetch` / `openapi-react-query` clients in `frontend/packages/syntara-ui/src/client.tsx` and `frontend/packages/syntara-ui/src/routes/access/accessClient.ts`. Direct use of `fetch()`, `XMLHttpRequest`, or `axios` is prohibited.

**Why:** Typed clients ensure the frontend can only call endpoints that exist in the OpenAPI spec. Raw HTTP calls bypass type safety and can hit undocumented or non-existent endpoints, silently breaking UI-API parity.

**Client pattern:**

```typescript
import createFetchClient from 'openapi-fetch'
import createClient from 'openapi-react-query'
import type { WorkflowAPI } from '@syntara/contracts'

const workflowFetchClient = createFetchClient<WorkflowAPI.paths>({ baseUrl: '/api/v1/' })
workflowFetchClient.use(authMiddleware)
export const workflowClient = createClient(workflowFetchClient)
```

- `client.tsx` — domain clients (workflows, executions, auth, settings, etc.)
- `accessClient.ts` — merged RBAC/access client (`ProjectsAPI`, `RolesAPI`, `AuthzAPI`, etc.)
- Exported `*FetchClient` instances — direct `.GET()` / `.POST()` when needed (e.g. file downloads, upload progress)

All clients apply `authMiddleware` from `client.tsx`, which handles token injection and 401 refresh/retry.

**Enforcement:**

| Mechanism | Scope | Behavior |
|-----------|-------|----------|
| ESLint rule `nexus/no-raw-http-calls` | `frontend/packages/syntara-ui/` | Blocks `fetch()`, `XMLHttpRequest`, and `axios` imports at lint time |
| `allowedFiles` config | ESLint config | Exempts specific files (e.g., `useFileUploadWithProgress.ts` for upload progress via XMLHttpRequest) |
| Inline `eslint-disable-next-line` | Per-call | Requires justification after `--` (e.g., `-- pre-auth call before token middleware`) |

**Rule source:** `frontend/packages/syntara-ui/eslint-plugin-syntara/rules/no-raw-http-calls.js`

## Contract Generation

The backend OpenAPI spec is the single source of truth. Frontend TypeScript types are **generated**, never hand-written.

**Tool:** `openapi-typescript`

**Input:** Backend domain sub-specs under `backend/src/syntara/schemas/` — see the `gen:local:*` scripts in `frontend/packages/syntara-contracts/package.json` for the exact source file per domain (e.g. `workflows/v2/openapi.yaml`, `authz/role.openapi.yaml`). The bundler also discovers additional sub-specs not listed there.

**Output:** `frontend/packages/syntara-contracts/src/*.ts` (plus node-output schemas and mock-api example fixtures generated by auxiliary scripts)

**Commands:**

```bash
# From repository root
make gen-contracts

# From frontend/ directory
npm run gen
```

The `gen:local` script runs `openapi-typescript` concurrently for each domain spec, then runs `npm run format` (Prettier) on the frontend workspace. Regenerate any time a backend OpenAPI sub-spec changes.

For details on the backend spec workflow (sub-specs, bundling, drift detection), see [OpenAPI Spec Management](openapi-spec-management.md).

## Full-Stack PR Workflow

In the monorepo, backend spec changes and frontend contract updates land in **one PR**. There is no separate "companion PR" — all changes ship together.

**Steps:**

1. Edit the relevant backend domain sub-spec under `backend/src/syntara/schemas/`
2. Run `make api-spec-bundle` to regenerate the bundled spec (`backend/src/syntara/schemas/openapi.yaml`)
3. Run `make gen-contracts` to regenerate TypeScript types
4. Update frontend code to use the new/changed types
5. Include all changes (sub-spec + bundled spec + contracts + UI code) in one PR

**CI enforcement:**

| Check | When | Severity |
|-------|------|----------|
| Pre-commit `backend-check-openapi-breaking` | `openapi.yaml` changed | **Blocking** — requires `breaking-change-ack:` in the PR description when oasdiff detects breaking changes |
| `check-contract-regeneration.py` | PR touches `backend/src/syntara/schemas/openapi.yaml` (via `ci-backend.yml`) | **Informational** — posts a PR comment if contracts were not regenerated; does not fail the job |
| `openapi-breaking-changes` CI job | Same trigger | **Informational** — posts breaking-change analysis; the step uses `continue-on-error` |

The contract regeneration job runs only when the PR changes `backend/**` (see `ci-backend.yml` path filters).

**Scripts:** `backend/scripts/openapi/check-contract-regeneration.py`, `backend/scripts/openapi/check-breaking-changes.py`

## Exception Mechanism

Two exception markers can be added to the PR description for cases where the standard workflow does not apply:

### Skipping contract regeneration

```
no-contract-regen: <justification>
```

Use when a spec change has no impact on generated types — for example, updating endpoint descriptions, adding examples, or changing metadata. Minimum 10 characters of justification required. The legacy alias `no-ui-pr:` is also accepted.

**Severity:** Informational (does not block merge). CI still posts a notice acknowledging the exception.

### Acknowledging breaking changes

```
breaking-change-ack: <justification>
```

Required when oasdiff detects breaking changes (removed endpoints, changed types, removed fields). Minimum 20 characters explaining why the change is necessary, the migration path, and how the frontend was updated.

**Severity:** Blocking via the pre-commit hook `backend-check-openapi-breaking` (enforced in CI). CI reads the PR description through `OPENAPI_PR_BODY`.

Both markers are case-insensitive and checked by scripts in `backend/scripts/openapi/`.

## WebSocket Scope

WebSocket endpoints (`/ws/`) are for **server-initiated, read-only streaming** only:

- Execution event streams
- LLM token streams
- Real-time status updates

All CRUD operations use the REST API (`/api/v1/`). WebSocket is **not** a mutation path — the REST API is the complete interface for all create, read, update, and delete operations.

For WebSocket implementation standards (connection lifecycle, message formats, AsyncAPI specs), see [WebSocket Standards](websocket.md).

## Drift Detection

Multiple layers detect when contracts fall out of sync with the backend spec:

| Layer | Trigger | Behavior |
|-------|---------|----------|
| Pre-commit hook `backend-api-spec-drift` | Backend `.py` files changed | Compares committed spec to live FastAPI schema; **blocking** in CI via the `pre-commit` job |
| CI `check-contract-regeneration.py` | PR touching `openapi.yaml` | Posts warning if contracts not regenerated (informational) |
| Scheduled workflow `check-contract-drift.yml` | Weekly (Tuesday 9:00 AM EST) | Regenerates contracts, auto-files GitHub Issue if drift detected |
| `make api-spec-drift` | Manual | Compares committed spec against generated spec with detailed diff |

The scheduled workflow auto-closes drift issues when the drift is resolved.

## Quick Reference

| Rule | Enforced By | Exception |
|------|-------------|-----------|
| Use typed API clients only | ESLint `nexus/no-raw-http-calls` | `eslint-disable-next-line` with justification |
| Regenerate contracts when spec changes | CI warning + weekly drift check | `no-contract-regen: <justification>` in PR description |
| Acknowledge breaking API changes | Pre-commit `backend-check-openapi-breaking` | `breaking-change-ack: <justification>` in PR description |
| WebSocket is read-only streaming | Convention (see [WebSocket Standards](websocket.md)) | N/A — REST is the complete CRUD interface |
| Backend + frontend changes in one PR | CI warning if contracts stale | `no-contract-regen: <justification>` for spec-only changes |
