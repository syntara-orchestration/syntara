Script step security review
===========================

- Review status: Proposed for Product Security review; not approved.
- Scope: User-supplied Python and Bash executed as a Syntara workflow Script step through the Execution Plane (EP).
- Related design: EP architecture overview (https://github.com/syntara-orchestration/syntara-execution-plane/pull/169), AO integration AAP-98873, execution epic ANSTRAT-1803, SDK contracts ANSTRAT-2422.

Review request
--------------

Please assess whether the isolation and controls below are sufficient for running user-supplied scripts in customer OpenShift clusters. In particular, decide whether a restricted Kubernetes Pod is an acceptable security boundary for arbitrary code, whether the network and credential boundaries are adequate, and which mitigations must block release. Record findings by severity, delivery impact, owner, and release-blocking status.

This document is intentionally limited to Script execution. It does not restate the full AO or EP architecture.

Script execution flow
---------------------

SCRIPT EXECUTION FLOW
1. Temporal workflow calls AO Script activity: Schedule Script node
2. AO Script activity performs: Validate inputs and select approved image digest/revision
3. AO Script activity calls EP Client supplied to AO: Submit work.execute
4. EP Client supplied to AO calls EP API and Work Store: Call EP supported API/command
5. EP API and Work Store returns to EP Client supplied to AO: Accepted WorkItem reference
6. EP API and Work Store calls EP worker: Claim one attempt
7. EP worker calls AO credential resolver: credential.resolve for OpenShift Cluster access
8. AO credential resolver returns to EP worker: Short-lived Cluster credential
9. EP worker calls Customer OpenShift API: Create per-attempt NetworkPolicy and Job
10. Customer OpenShift API returns to EP worker: Owned Job and Pod
11. EP worker calls Per-attempt workload Pod: SDK Health, then one Execute stream
12. Per-attempt workload Pod calls Python or Bash process: Start script subprocess
13. Python or Bash process returns to Per-attempt workload Pod: Exit status and bounded stdout/stderr
14. Per-attempt workload Pod returns to EP worker: Terminal SDK Result or Failure
15. EP worker calls EP API and Work Store: Persist result before cleanup
16. EP worker calls Customer OpenShift API: Delete owned Job and NetworkPolicy
17. EP API and Work Store calls AO completion handler: work.execute.completed callback
18. AO completion handler calls Temporal workflow: Complete activity with workflow output

The EP Client is a library supplied by EP for AO to call EP. It is not an additional runtime service and does not execute the script. Its package/version, exact API, authentication, and retry contract must be recorded in AAP-98873.

Security boundary
-----------------

The script source and its inputs are untrusted. The intended isolation boundary is one EP-created Kubernetes Job and Pod per work-item attempt. The SDK runtime receives the invocation and starts Python or Bash as a child process inside that Pod.

The child process shares the Pod's container identity, filesystem, and network namespace with the SDK runtime. It is not a separate OS security principal or a general-purpose sandbox. Product Security must decide whether the Pod controls listed below are sufficient for the supported threat model or whether stronger isolation is required.

Controls in the EP workload design
----------------------------------

Area: Workload lifecycle
Current EP design evidence: One Job completion and one parallel Pod per attempt; backoffLimit: 0; deterministic attempt identity; bounded active deadline; one-hour Job TTL as cleanup backstop.

Area: Pod privileges
Current EP design evidence: Non-root execution, RuntimeDefault seccomp, no service-account token, no privilege escalation, all Linux capabilities dropped, read-only root filesystem.

Area: Compute and temporary storage
Current EP design evidence: CPU request 100m and limit 1 CPU; memory request 128 MiB and limit 512 MiB; memory-backed /tmp capped at 64 MiB.

Area: Network
Current EP design evidence: Per-attempt NetworkPolicy denies ingress and allows DNS plus configured egress ranges, excluding forbidden ranges. Customer CNI enforcement must be validated.

Area: Workload transport
Current EP design evidence: EP uses the Kubernetes API port-forward to the owned Pod. The SDK gRPC channel must authenticate peers and protect confidentiality; production mTLS wiring must be verified for the target deployment.

Area: Result handling
Current EP design evidence: EP persists a terminal result before cleanup. Cleanup status is tracked separately. An uncertain result after Execute submission is reconciled, not automatically replayed.

These are controls in EP's implementation/design evidence, not a claim that every customer cluster enforces them. The target cluster's CNI, admission policies, quotas, registry access, and supported OpenShift versions require deployment validation.

Inputs, credentials, and outputs
--------------------------------

Data: Script code and environment
Handling and boundary: Ordinary, untrusted workflow input sent to the SDK Execute request and then to the child process. Environment values are not a secret-delivery mechanism. Avoid putting secrets here.

Data: OpenShift Cluster credential
Handling and boundary: AO resolves an opaque reference for EP. EP uses the short-lived value to access the customer Kubernetes API. It must not enter the WorkItem payload, workload Pod spec/environment, script process, result, or logs.

Data: Workload credential
Handling and boundary: Separate from the Cluster credential. The SDK supports invocation-scoped credential callbacks, but current EP evidence says bound workload credentials are unavailable. Script manifests do not currently declare credential recipes. Do not claim Script credential delivery is available.

Data: AO/EP control-plane secrets
Handling and boundary: Service JWTs, callback mTLS material, database credentials/encryption keys, and EP TLS material stay in AO/EP service secret stores. They are never workload inputs.

Data: Script output
Handling and boundary: return_code, stdout, stderr, and Python stdout_json may contain arbitrary or sensitive data. Treat as untrusted; enforce limits and access controls; do not log full output. EP stores the result and AO maps it to workflow output.

Script-specific limits and failure behavior
-------------------------------------------

Concern: Output
Current step/runtime contract: Default capture is 276,480 bytes (270 KiB) per stream; configurable up to 1 MiB per stream. Combined serialized SDK result is capped at 1 MiB. Excess stream data is drained and truncated; a result that still exceeds the SDK limit fails.
Security requirement for review: Confirm truncation/failure semantics and ensure AO, EP, and Temporal payload limits are compatible.

Concern: Memory and CPU
Current step/runtime contract: Pod limit is 512 MiB and 1 CPU. The script launcher attempts an address-space cap derived from the cgroup.
Security requirement for review: Confirm these defaults and identify any additional CPU-time, process-count, ephemeral-storage, or file-size controls required.

Concern: Timeout
Current step/runtime contract: Invocation timeout is sent to the SDK; Pod active deadline covers startup, execution, and termination grace. Cleanup has its own bounded period.
Security requirement for review: Confirm maximum duration and that AO activity deadlines include EP startup, callback, and cleanup slack.

Concern: Cancellation
Current step/runtime contract: EP sends SDK Cancel, waits a bounded grace period, then deletes the owned Job. Script cleanup sends TERM then KILL to the child process group.
Security requirement for review: Test ignored cancellation and descendants; distinguish cancellation before Execute from cancellation after it may have started.

Concern: Retry
Current step/runtime contract: EP submits Execute once per attempt. Before submission, confirmed infrastructure failures may be retried. After possible submission, a missing result is uncertain and must not cause automatic replay.
Security requirement for review: Arbitrary scripts can have external side effects; confirm AO does not silently retry uncertain or non-idempotent executions.

Concern: Cleanup
Current step/runtime contract: EP deletes the owned Job, then its policy; TTL is a backstop and does not clean policies. A reconciler removes orphan policies only after confirming the Job/Pods are absent.
Security requirement for review: Confirm cleanup failure remains visible, retryable, and operationally actionable without overwriting a committed result.

Current implementation gap
--------------------------

The Syntara feat/ANSTRAT-2523 base includes a direct AO-worker-to-OpenShift Script path. The target flow in this review uses the EP-provided Client and EP-managed workload lifecycle. The AO-to-EP Client integration and a shared-cluster AO→EP→Script trace are not demonstrated by this document. AAP-98873 must link that implementation and end-to-end evidence before the target flow is treated as shipped.

EP selects the image supplied by the caller; EP's current design does not independently enforce image provenance. AO/packaging must provide a release-approved immutable image digest and prevent workflow authors from selecting arbitrary images or target namespaces. The client/API contract and trusted image mapping remain open integration decisions.

Decisions requested from Product Security
-----------------------------------------

1. Is the per-attempt Pod, with the listed restrictions, an adequate boundary for arbitrary Python/Bash code? If not, specify the required stronger isolation mechanism and release gate.
2. Are the customer-controlled egress policy and CNI validation sufficient? Specify the required default-deny behavior and evidence for supported clusters.
3. Are the credential separation and output handling acceptable? Confirm that Script receives no protected workload credentials and that outputs/errors are treated as potentially sensitive.
4. Which controls must be verified before release for image provenance, SDK gRPC TLS/mTLS, resource limits, cancellation, uncertain outcomes, and cleanup?
